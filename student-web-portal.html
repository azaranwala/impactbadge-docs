Student Web Portal

10 pages for Chromebook & laptop access — solves no-cell-phone policy blocker. Deployed September 2026.

Problem Solved

Many K-12 schools have strict no-cell-phone policies in classrooms. Without a web portal, students could only use ImpactBadge on their mobile apps before/after school. The student web portal enables full access from school Chromebooks and laptops — removing the primary blocker for school-wide rollouts.

Login Flow

  1. Student goes to impacthub-prod.web.app
  2. Clicks "Login" button (top-right nav bar, always visible)
  3. Enters email + password (or signs in with Clever SSO)
  4. Clicks "Sign In"
  5. Automatically routed to /student dashboard

Note: The Login and Sign In buttons use inline style={{ background: "#00897B" }} because Tailwind CSS 4's bg-teal-primary custom class doesn't resolve without a config file. All brand-color buttons in the web portal must use inline styles.

Architecture

Same app, role-based routing. The student portal lives inside the existing React app at impacthub-prod.web.app. When a student logs in, they're automatically routed to /student/* pages with a student-specific layout. Admin users continue to see their existing admin dashboards — zero impact on existing functionality.

Zero backend changes. All 10 student pages call existing Cloud Functions that were already deployed for the mobile apps. No new API endpoints were created.

Student Layout

Desktop (Chromebook): Left sidebar with navigation, XP progress bar, level badge, quick stats (hours/badges/streak), and sign out button.

Tablet / Mobile: Bottom tab bar with 5 nav items + compact header with level and XP.

Gamification always visible: XP bar with gradient fill (teal → orange), level number, tier name (Newcomer → Luminary), and streak count in the sidebar.

Check-In Flow (No GPS Needed)

School Chromebooks typically don't share location. The web portal uses PIN-only check-in:

  1. Teacher shares the 4-digit event PIN with students
  2. Student goes to Check In page (/student/checkin)
  3. Enters the 4 digits (auto-advances between inputs)
  4. Click "Check In" — verified instantly
  5. When done, go to Check Out to log hours

No GPS, no QR scanner, no camera needed — works on any device with a keyboard.

Self-Reported Kind Deeds

Students (or parents for K-5) can log volunteer activities and acts of kindness that happen outside structured events:

  • Description: What they did (minimum 10 characters)
  • Date: When it happened (cannot be future)
  • Hours: 0.5 to 24 hours
  • Organization: Optional (defaults to "Self-reported")

Submissions go to the teacher/admin for verification before counting toward the student's total.

Event Discovery Defaults

Since school Chromebooks don't have GPS, the event discovery page defaults to school coordinates (currently set to Holland, MI for Black River). Students can search by name or filter by category to find events.

8 category filters: Environment 🌳, Education 📚, Health 🏥, Animals 🐾, Hunger 🍽️, Arts 🎨, Seniors 👴, Community 🏘️

Isolation from Admin Portal

Zero risk to existing admin functionality. The student portal:

  • Uses a separate StudentLayout component (admin uses Layout)
  • Has separate routes (/student/* vs /admin/*, /school/*, etc.)
  • Calls the same Cloud Functions but cannot access admin-only endpoints (server-side role checks)
  • Shares the same Firebase config and auth system
  • Deployed via firebase deploy --only hosting (never touches Cloud Functions)
